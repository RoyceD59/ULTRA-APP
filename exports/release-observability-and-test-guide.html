The current health endpoint reports application liveness. It does not certify the database, external providers, security behavior or candidate identity.

Fresh, agreeing snapshots

node --input-type=module <<'JS'
import { verifyLiveApi } from './infra/cloudflare/forest/consistency-handoff.mjs';
console.log(JSON.stringify(await verifyLiveApi(), null, 2));
JS

Pass requires HTTP success on both hosts, valid JSON and the exact compatible contract: 64-character hex snapshot ID; positive integer adjustment revision; maxAgeSeconds: 60; boolean lifespan availability; nonnegative finite totals; calculation within the validator's freshness/future-clock bounds. Both hosts must agree on comparison fields; their calculation timestamps may differ.

Timeout, stale calculation, incompatible fields, disagreement or an old zero fallback blocks advancement. An unavailable probe does not prove downtime. Capture UTC time and check clock accuracy before interpreting age failures.

Source identity — currently an evidence gap

Do not assume /version.json exists on the API. Do not accept a 200 HTML fallback as revision JSON. The Companion version at https://app.ucfilters.com/version.json describes the client baseline checked by the build script, not the running API's security implementation.

Require trustworthy build-to-runtime provenance or an owner-approved API attestation mechanism identifying the candidate. A health response, matching global totals, client version, or configured environment string alone does not prove which API executable is serving traffic.

If this linkage is unavailable, mark source verification blocked. Do not claim the sign-in/upload protections are live or add production diagnostics without approval.

6. Signed-in and upload smoke tests

Production writes require separate approval and designated test accounts/media. Never deactivate real staff, forge production bearers, or upload adversarial files to public storage merely to demonstrate protection.

On an isolated staging environment using the retained candidate:

• Confirm an ordinary fresh login can access its authorized resources.
• Confirm a controlled old expiry-free session is rejected and signing in again

restores access. Test expiry boundaries through fixtures rather than waiting eight hours or changing a production clock.

• Confirm customer A cannot attach customer B's media.
• Try approved valid media and controlled invalid MIME/signature cases.

Confirm invalid attachments are rejected, not silently accepted.

• Check original and derivative response headers and download behavior.
• Confirm deactivated/deleted test team identities lose customer-count access.
• Remove authorized test fixtures and verify no production customers changed.

For a browser check, verify rejection messages are visible and recovery is usable, not just that the network request failed. Record native/device checks separately; local API tests do not certify physical-phone usability.

7. Ongoing observability

For each implementation, monitor a small set of signals:

SignalInterpretation and action
Per-host health status and latencyInvestigate sustained errors/timeouts; compare hosts before blaming application code
Snapshot contract, age and agreementBlock client advancement on failure; inspect cache/calculation logs
Auth rejection ratesExpect a temporary rise after legacy-session expiry; investigate sustained fresh-login failures
Upload/attachment rejection ratesDistinguish invalid media from valid-file failures; inspect sanitized reason codes
Request 5xx, background-job failuresCorrelate to publishing/startup time and operation; do not silently replay payments or notifications
Runtime memory/CPU and startup failuresCompare to pre-release baseline and inspect worker/module errors

These are monitoring recommendations, not a claim that new metrics, alerts, health dependencies or dashboards have been installed. Establish baselines and owner-approved thresholds before activating alerts.

Prefer structured logs with UTC timestamp, service, operation, request ID, status, duration and a sanitized error category. Never log Authorization headers, cookies, reset tokens, signed upload URLs, passwords, connection strings, email/phone/address or full request bodies. Public errors must not reveal internal paths, stack traces or database details.

8. Release decision and recovery

Mark each gate passed, failed, or unverified, with evidence:

• [ ] Exact source selection and separate API publication approval.
• [ ] Retained candidate tests and compilation.
• [ ] Successful candidate publishing and actual image-size evidence.
• [ ] Currently served API linked to candidate.
• [ ] Fresh, compatible, agreeing public snapshots after publication.
• [ ] Approved signed-in/upload smoke checks, or explicit untested scope.
• [ ] No unexpected error/resource regression in the observation window.
• [ ] Separate approval before any client advancement.
• [ ] Separate approval before production initialization/schema changes.

If a gate fails, stop advancement. Preserve the evidence and retained predecessor; obtain owner approval for any rollback or operational changes. Do not turn an unavailable check into an assumed pass.
