4. CMS design proposal

Recommended: extend the existing ProjectHub CMS, not install a replacement. Existing merged blog code already includes draft/review/publish/reject actions, history and published snapshots. Guide administration also exists. WooCommerce remains authoritative for products, prices, stock and orders.

Options and trade-offs

  1. Existing CMS extension — recommended. Lowest migration risk; reuse team permissions, editorial workflow, API/database and media storage. Improve staff usability and unify navigation only where the audit identifies gaps.
  2. Shared editorial workspace for blog and guides. Consistent editor/media/preview controls, while keeping separate blog and guide data models. More work, but avoids replacing working publishing logic.
  3. External headless CMS. Consider only if current authoring/localization requirements exceed the existing tools. Adds migration, preview, authentication, integration and synchronization costs; not justified by current evidence.

Recommended staff-facing structure

  • Content: blog and guide lists, search, status filters and draft editing.
  • Review: editorial feedback, approval queue and preview, retaining existing publishing permissions.
  • Media: approved uploads, alt text, image sizes and links; reuse existing storage verification.
  • History: revisions and audit trail; restoring a revision must be explicitly confirmed.
  • Read delivery: public clients receive published snapshots only; failed revisions must not remove current live content.

Data flow: staff draft → authorized review/publish → published snapshot → cached public API → Companion. Product references use WooCommerce IDs/URLs, not copied prices or inventory. Public drafts stay private, private response caches are user-scoped, and successful publishing invalidates relevant cached content. This is a design for approval, not a statement that all listed capabilities need to be newly built.

Phase 1 — reliability before speed

Fix the map timer crash, checkout overlap and supported-origin/deep-link routing. Add focused regressions for correct timer receiver/cleanup, route reloads and controlled mobile layouts. Confirm no uncaught errors and no essential control blocked by an overlay.

Phase 2 — establish a real mobile baseline

Measure cold/warm Home, catalogue, product, blog and guide journeys on agreed low-end Android and iPhone/network profiles. Record compressed bytes, JavaScript parse/startup, LCP, INP, CLS, API percentiles, requests and image transfer. Proposed targets: LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1; these are goals, not current scores.

Phase 3 — reduce startup and repeated work

Profile heavy route modules and root providers before changing them. Separate admin-only/heavy modules where supported; defer unused media/native functionality. Aim for at least 30% lower initial transfer/parse cost against the baseline without breaking Expo routing or native builds. Keep versioned public assets cacheable where privacy permits; do not apply public caching to authenticated data.

Phase 4 — catalogue and freshness

Profile WooCommerce fetches, use bounded normalized catalogue caching and targeted invalidation after updates, avoid duplicate refetches, and consider server-side filtered paging. Targets: at least 50% lower warm response latency and 80% fewer repeated upstream reads under the chosen test scenario. Preserve complete catalogue pagination or fail explicitly; keep checkout price/stock authoritative.

Phase 5 — media and published content

Reuse existing image derivatives, correctly size product/feed images, reserve dimensions and defer below-fold video. Proposed image targets: median catalogue image ≤150 KB, main image ≤250 KB. Validate existing published-snapshot/ETag caching rather than duplicating it; publishing should become visible within the agreed freshness window (initial proposal ≤60 seconds).

6. Completion gates

  • Every customer/admin route has an explicit tested result or named blocker; no blanket pass from screen rendering alone.
  • Core browser journeys have no crashes, indefinite loading or tap-blocking overlays. Direct entry and Back work on supported origins.
  • Controlled signed-in customer/admin fixtures cover account, QR, rewards, forms, password flows and Alison real answer/timeout/retry without changing customer data.
  • Real native iOS and Android sessions cover signed-out/in navigation, basket direct entry, safe areas, keyboard, camera/QR and Alison. Browser simulations cannot close this gate.
  • Payment/order submission remains outside this audit; any future such testing must use a controlled sandbox, never an accidental live order.
