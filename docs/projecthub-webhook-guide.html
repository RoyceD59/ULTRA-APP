🗺 1 — What these tools do

ProjectHub has two complementary bridges between external systems and internal work:

📡 Webhook Ingestion

External tools (Jira, Salesforce, n8n, Make, custom scripts) push task payloads into ProjectHub automatically. Tasks appear in the board instantly — no manual entry.

🤖 Agent Dispatch

Team members push an existing task to an AI agent worker from the task card. The agent receives the full task context and can act on it autonomously.

🧪 2 — Webhook Tester (inside ProjectHub)

Navigate to Webhook Tester in the ProjectHub sidebar (the amber 📡 icon). The page lets any authenticated team member fire a test payload against the live server without needing the webhook secret or an external tool.

How it works

  • Fill in Source Platform — identifies which system the event is pretending to come from (e.g. jira, salesforce, n8n).
  • Fill in Event Name — the lifecycle event being simulated. The only event that creates a task today is task.created.
  • Edit the Task Data JSON textarea — this is the task payload. See the schema reference below for all recognised fields.
  • Click Send Payload. The server validates the payload, (optionally) creates the task, and returns a JSON response displayed in the Response panel on the right.
ℹ️
No HMAC needed in the Tester The Tester posts to POST /api/webhook/test-dispatch, an authenticated team-only route. The server signs the ingest internally on your behalf, so you never handle the webhook secret in the browser. The exact same validation logic runs as on the public endpoint.

Default payload loaded in the form

{
  "event": "task.created",
  "sourcePlatform": "jira",
  "taskData": {
    "title": "Update API documentation",
    "description": "Sync swagger docs with recent code changes",
    "priority": "high"
  }
}
⚠️
The default payload will fail validation The defaults above are missing three required fields: assigneeId, resourceRequired, and deliveryFormat. You will see a 400 response with a validationErrors array until all three are present. See the schema table below.

A payload that passes

{
  "event": "task.created",
  "sourcePlatform": "jira",
  "taskData": {
    "title": "Refactor authentication module",
    "description": "Split auth.ts into separate login, token, and session files.",
    "assigneeId": 3,
    "projectId": 1,
    "priority": "high",
    "resourceRequired": true,
    "deliveryFormat": "pull_request",
    "dueDate": "2026-09-15",
    "notifyVia": "email"
  }
}

A successful response looks like:

{
  "accepted": true,
  "taskId": 42,
  "message": "Event 'task.created' from 'jira' accepted",
  "validationErrors": []
}

🌐 3 — Live Webhook Ingest (external systems)

To push tasks from a real external system, call the public endpoint with an HMAC-SHA256 signature:

POST HMAC required /api/webhook/ingest

Authentication — HMAC-SHA256

Every request must include an X-Webhook-Signature header. The value is the HMAC-SHA256 digest of the exact raw request body bytes, computed using the shared PROJECTHUB_WEBHOOK_SECRET.

# bash example (curl)
SECRET="your-webhook-secret"
BODY='{"event":"task.created","sourcePlatform":"n8n","taskData":{...}}'

SIG=$(echo -n "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | awk '{print $2}')

curl -X POST https://your-projecthub-domain/api/webhook/ingest \
  -H "Content-Type: application/json" \
  -H "X-Webhook-Signature: sha256=$SIG" \
  -d "$BODY"
⚠️
Sign the exact bytes you send Do not re-serialise the payload before signing — use the same bytes that go over the wire. Re-serialising (e.g. JSON.stringify(JSON.parse(body))) may produce a different key order or whitespace, causing the HMAC to fail for a valid request.

Node.js / n8n example

import { createHmac } from "crypto";

const secret = process.env.PROJECTHUB_WEBHOOK_SECRET;
const body   = JSON.stringify(payload);          // do not re-parse before signing
const sig    = createHmac("sha256", secret).update(body).digest("hex");

await fetch("https://your-domain/api/webhook/ingest", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Webhook-Signature": `sha256=${sig}`,
  },
  body,
});

Error responses for bad signatures

503 — secret not configured
{"error":"Webhook ingestion is not available: webhook secret is not configured."}
401 — wrong or missing signature
{"error":"Invalid or missing webhook signature"}

📋 4 — Full payload schema

Top-level envelope

FieldTypeRequired?Description
eventstringRequiredLifecycle event name. Use task.created to create a task.
sourcePlatformstringRequiredIdentifies the sending system, e.g. jira, salesforce, n8n. Updates the System Status watchdog for this platform.
taskDataobjectOptionalTask fields. If present, all three business-logic required fields inside must also be present. Omit entirely to ping the system status without creating a task.
metaanyOptionalArbitrary metadata for logging or future routing. Not persisted to the task.

taskData fields

FieldTypeRequired?Notes
titlestringRequiredTask name. Also required (with projectId) for the task row to be inserted.
assigneeIdinteger | nullRequired (non-null)Numeric ID of the team member from the Members page. Must not be null or missing.
resourceRequiredbooleanRequired (truthy)Flags whether external resources (tools, budget, third-party access) are needed.
deliveryFormatstringRequiredHow the task output will be delivered. Examples: pull_request, report, document, design_file.
projectIdintegerOptional*Links the task to a project. Without this, the task is accepted but not inserted into the board.
descriptionstringOptionalDetailed context. Defaults to empty string.
statusstringOptionaltodo | in_progress | review | done. Defaults to todo.
prioritystringOptionallow | medium | high | urgent. Defaults to medium.
dueDatestring | nullOptionalISO date string, e.g. "2026-09-30".
notifyViastringOptionalComma-separated notification channels: "email", "whatsapp", "slack".

* A task with taskData but no projectId passes validation and returns accepted: true with taskId: null — nothing is written to the board.

📨 5 — Response shape & validation errors

Every response from both /webhook/ingest and /webhook/test-dispatch follows the same shape:

{
  "accepted":        boolean,
  "taskId":          number | null,
  "message":         string,
  "validationErrors": string[]     // empty array on success
}

Validation error example

// Request with only title and description (missing 3 required fields)
→  HTTP 400
{
  "accepted": false,
  "taskId": null,
  "message": "Validation failed — missing required fields",
  "validationErrors": [
    "taskData.assigneeId is required",
    "taskData.resourceRequired is required",
    "taskData.deliveryFormat is required"
  ]
}

Success — task created

// All required fields present, projectId and title provided
→  HTTP 200
{
  "accepted": true,
  "taskId": 42,
  "message": "Event 'task.created' from 'jira' accepted",
  "validationErrors": []
}

Success — ping only (no taskData)

// Payload with no taskData — updates System Status only
→  HTTP 200
{
  "accepted": true,
  "taskId": null,
  "message": "Event 'heartbeat' from 'salesforce' accepted",
  "validationErrors": []
}

🤖 6 — Push Task to Agent (AI team dispatch)

Once a task exists on the board — whether created manually, imported by webhook, or via the task form — any team member can dispatch it to an AI agent worker.

How to dispatch from ProjectHub

  • Open the Tasks page and find the task you want to dispatch.
  • Click the task's action menu (three-dot menu or the task detail panel) and select Push to Agent. A dialog opens.
  • The dialog lists all available agent workers (fetched live from GET /api/ai/agents). Each card shows the agent's name and role.
  • Select the target agent and click Push to Agent.
  • A success toast confirms dispatch. The agent receives the full task context via the orchestrator webhook.

What the agent receives

The server builds an outbound payload and forwards it to the configured orchestrator URL (AI_ORCHESTRATOR_WEBHOOK_URL) with an HMAC signature:

{
  "source": "projecthub",
  "type": "task_dispatch",
  "pushId": "uuid",
  "task": {
    "id": 42,
    "title": "Refactor authentication module",
    "description": "Split auth.ts into separate files.",
    "status": "todo",
    "priority": "high",
    "assigneeId": 3,
    "dueDate": "2026-09-15",
    "sourcePlatform": "jira",
    "resourceRequired": true,
    "deliveryFormat": "pull_request",
    "notifyVia": "email",
    "targetAgent": "Replit Agent",
    "targetAgentId": 1
  }
}

Dispatch audit trail

Every dispatch attempt is written to the ai_push_events table with status pending → sent | failed. The Push Task monitoring page shows the history, outcome, and timestamp of every dispatch. Failures trigger an internal alert so no dispatch can silently disappear.

Endpoint reference

GET Team auth
/api/ai/agents

Returns the list of registered agent workers. Each item has id, name, role, status.

POST Team auth
/api/ai/push-task

Dispatches a task to an agent. Body: { taskId, agentId, agentName }. Returns { success, message, sentAt, pushId }.

💚 7 — System Status integration

Every accepted webhook — even a payload with no taskData — updates the system_status table for the sourcePlatform value. This powers the System Status page in ProjectHub, which shows which external systems are actively connected and when they last synced.

Use case: heartbeat pings

Schedule a lightweight webhook every 5–15 minutes from each external system using only the required envelope fields and no taskData. ProjectHub will mark that platform as connected and update lastSync. The team can immediately spot a disconnected integration without needing to trace logs. 

{
  "event": "heartbeat",
  "sourcePlatform": "salesforce"
}

🔁 8 — End-to-end example walkthrough

The scenario: an n8n automation detects a new Jira ticket and should create a matching task in ProjectHub, assigned to a team member, and then dispatch it to an AI agent for initial research.

Step 1 — Look up the assignee ID

In ProjectHub, open Team → note the numeric ID next to the member you want. Example: David — ID 3.

Step 2 — Look up the project ID

Open Projects → hover or open the target project. The URL or project detail shows the numeric ID. Example: Q4 Roadmap — ID 1.

Step 3 — Test the payload in the Webhook Tester

{
  "event": "task.created",
  "sourcePlatform": "jira",
  "taskData": {
    "title": "Investigate Jira-9821: Auth timeout on mobile",
    "description": "Users report auth tokens expiring after 10 min on iOS. Jira ref: PROJ-9821.",
    "assigneeId": 3,
    "projectId": 1,
    "priority": "urgent",
    "resourceRequired": true,
    "deliveryFormat": "report",
    "dueDate": "2026-08-29",
    "notifyVia": "email"
  }
}

Confirm the Response panel shows "accepted": true and a taskId.

Step 4 — Verify the task appeared on the board

Go to Tasks → the new task should be visible under the selected project, assigned to David, marked Urgent.

Step 5 — Push to the AI agent

Open the task, click Push to Agent, select the target agent, and confirm. The agent receives the full task JSON and begins working.

Step 6 — Wire n8n to the live endpoint

Replace the Tester with an n8n HTTP Request node:

URL:     https://your-projecthub-domain/api/webhook/ingest
Method:  POST
Headers:
  Content-Type:        application/json
  X-Webhook-Signature: sha256={{ $hmacSha256(JSON.stringify($json.body), $env.PROJECTHUB_WEBHOOK_SECRET) }}
Body:    {{ JSON.stringify($json.body) }}

💡 9 — Tips, limits & security notes

Security

  • The PROJECTHUB_WEBHOOK_SECRET is a shared secret — treat it like a password. Rotate it if it leaks.
  • The Tester route (/webhook/test-dispatch) never exposes the secret to the browser. It reuses team JWT auth so only logged-in team members can fire test payloads.
  • HMAC verification uses timingSafeEqual to prevent timing-based signature guessing.
  • If PROJECTHUB_WEBHOOK_SECRET is not set, both routes return 503 — there is no unauthenticated processing path.

Common pitfalls

  • Missing projectId — a valid payload with all three required fields but no projectId returns accepted: true, taskId: null. The task is not created.
  • assigneeId: null — explicitly setting null fails validation the same as omitting the field. Must be a non-null integer.
  • Re-serialising before signing — always sign the original body string, not a re-parsed version of it.
  • Wrong assigneeId — IDs are internal numeric IDs, not usernames or email addresses. Check the Team page.

Rate limiting

Both ingest routes share the API server's global rate limiter. For high-volume integrations, send payloads in batches or back off on 429 responses.

✅
Assignment emails on webhook-created tasks Tasks created through the webhook ingest route are written directly to the database and do not currently trigger the automatic assignment email that fires on the task create/update UI form. To send an assignment notification, update the task via the ProjectHub task edit flow after it is created.
