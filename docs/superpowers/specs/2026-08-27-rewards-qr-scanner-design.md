# ProjectHub Rewards QR Scanner

Date: 2026-08-27

## Goal

Give authorized ProjectHub staff a fast, safe way to scan a customer's Rewards QR
code and award or redeem points that immediately appear in the customer's Ultra
Clear Companion account.

The feature must extend the existing UC Rewards ledger and customer balance
surfaces. It must not create a second points balance or bypass the existing
admin authentication model.

## Users and permissions

- Any active ProjectHub team admin may:
  - Open the Rewards scanner.
  - Request camera access and scan a customer's QR code.
  - Review the resolved customer and current balance.
  - Award points or redeem points.
  - View the resulting transaction and ledger history.
- Only the primary/super-admin may:
  - Change the points-to-value conversion configuration.
  - Enable or disable redemption rules.
- Permission checks are enforced on the API, not only in the ProjectHub UI.
- A non-admin, inactive, deleted, or unknown account cannot transact.

## QR identity and security

The current Companion QR value contains a raw account ID. Replace that value with
a signed, short-lived rewards token before using it for transactions.

The token should:

- Be generated by the API for the authenticated Companion account.
- Identify the account without exposing trusted profile fields.
- Include an expiration time and purpose/audience claim for rewards scanning.
- Be signed with a server-managed secret and verified server-side.
- Never be treated as proof of the customer's balance, name, phone, or points.
- Fail clearly when expired, malformed, revoked, or signed incorrectly.

The Companion account page will continue to display a QR code and explain that it
can be shown to field staff. ProjectHub will request camera permission before
starting the scanner and will provide a manual code/phone/email fallback for
unsupported browsers or camera-denied sessions. The fallback must use the same
server-side customer resolution and authorization rules.

## ProjectHub experience

Add a scanner workspace to the existing UC Rewards page rather than creating a
separate rewards product.

### Scan state

1. Staff selects **Scan customer**.
2. ProjectHub explains why camera access is needed and requests permission only
   when the staff starts scanning.
3. A camera preview shows an obvious scan frame and a cancel control.
4. A successful scan pauses the camera and sends the token to the API.
5. The UI shows the matched customer's first name, masked contact details,
   current balance, and a recent ledger summary.
6. Invalid, expired, duplicate, or unknown codes show an actionable error and
   allow another scan without a page refresh.

### Transaction state

The staff chooses **Award** or **Redeem**.

- Award:
  - Show common point presets plus a custom positive whole-number field.
  - Require a transaction reason.
  - Add a positive ledger entry.
- Redeem:
  - Show common 1,000-point-block presets plus a custom block count.
  - Only whole multiples of 1,000 points are accepted.
  - Block the transaction when the current balance is insufficient.
  - Show the configured KES or percentage equivalent before confirmation.
  - Add a negative ledger entry.

Both actions require a confirmation step with customer identity, direction,
points, conversion value where applicable, reason, and the staff member who will
be recorded as the actor. While the request is pending, controls are disabled.
On success, the updated balance and transaction receipt appear immediately, the
ledger is refreshed, and the scanner can be started for the next customer.

## Conversion configuration

Store the active redemption configuration in the database, with one rule per
conversion mode:

- Unit: exactly 1,000 points.
- Mode: `kes` or `percentage`.
- Value: a validated non-negative numeric value appropriate to the mode.
- Active status.
- Last editor and update timestamp.

The primary/super-admin can edit the mode and value in ProjectHub. The UI must
show an example such as “1,000 points = KES 100” or “1,000 points = 5%”.

Every redemption ledger entry stores a snapshot of the mode and value used at
the time of redemption. This keeps historical receipts accurate if the
configuration changes later.

## API and database behavior

Extend the existing `/uc/admin/rewards/*` route family.

Required behavior:

- Resolve and validate a signed QR token.
- Return a safe customer summary without exposing unnecessary personal data.
- Return the current balance from the ledger.
- Create award and redemption entries atomically.
- Lock or otherwise serialize the customer's balance check and redemption
  insert so two concurrent redemptions cannot overspend the same points.
- Reject invalid amounts, missing reasons, unauthorized roles, expired tokens,
  deleted accounts, and insufficient redemption balances with stable errors.
- Record the authenticated ProjectHub staff identity server-side; do not trust a
  client-supplied `grantedBy`.
- Send a Companion push notification for both awards and redemptions when the
  customer has a usable notification token. A notification failure must not
  roll back a successfully committed ledger transaction.
- Return the updated balance and inserted entry in the mutation response.

Update the OpenAPI contract and regenerate the shared clients before consuming
new endpoints from either frontend. Add the necessary database schema and
idempotency/concurrency protection using the existing migration conventions.

## Companion behavior

- Replace the raw-ID QR payload with the signed server-issued token.
- Keep the QR visible in the existing rewards card alongside the balance and
  recent history.
- Refresh the signed token when it expires or when the account screen reloads.
- After a ProjectHub transaction, the user's next rewards refresh shows the
  changed balance and ledger entry.
- Do not add a Companion-side redemption control in this scope; staff controls
  the transaction from ProjectHub.

## Error handling and abuse prevention

- Camera permission denied: explain how to enable access and offer manual lookup.
- Camera unavailable or unsupported: offer manual lookup without pretending that
  scanning is active.
- Invalid QR: identify it as invalid without revealing whether an account ID
  exists.
- Expired QR: ask the customer to refresh their Rewards screen and show a new
  code.
- Insufficient balance: show required points and current balance; do not create
  a ledger row.
- Double-submit or network retry: use an idempotency key for a transaction so
  a single staff confirmation cannot create duplicate entries.
- Rate-limit token resolution and mutations per authenticated staff account.
- Keep the scanner route behind the existing ProjectHub admin guard and repeat
  all sensitive checks in the API.

## Testing and acceptance criteria

### API tests

- Signed token issuance, valid verification, expiry, wrong purpose, and
  tampering.
- Admin-only access for scan, conversion, award, and redemption endpoints.
- Award with preset and custom amounts.
- Redemption accepts exactly 1,000-point multiples.
- Redemption rejects non-multiples, zero/negative values, and insufficient
  balances.
- Concurrent redemptions cannot produce a negative balance.
- Idempotent retry returns the original transaction rather than inserting a
  duplicate.
- Conversion mode/value validation and super-admin-only updates.
- Ledger entry records staff actor and conversion snapshot.
- Notification failures do not undo committed points.

### ProjectHub UI tests

- Scanner requests camera access only after activation.
- Camera success resolves a customer and shows the balance.
- Permission denial, unsupported camera, invalid QR, and expired QR all expose
  the manual fallback.
- Award and redeem flows show presets, custom validation, confirmation, loading,
  success, and failure states.
- Redemption is visibly blocked when the balance is too low.
- Balance and ledger update after a successful transaction.
- Conversion settings are hidden or read-only for ordinary team admins.

### Companion checks

- Rewards QR renders from the signed token.
- Refreshing the account screen obtains a usable token.
- A changed balance and ledger entry appear after a ProjectHub transaction.
- No native camera implementation is needed in Companion for this feature;
  ProjectHub is the scanner.

## Out of scope

- Customer self-service redemption inside Companion.
- Product-specific coupons or checkout discount application.
- Cash payouts.
- Changing existing automated reward rules unrelated to scanner transactions.
- A separate mobile staff application.
